# Gatherly — инструкции для Codex

Доработай существующий Gatherly. Перенеси бэкенд с C++/Drogon на Python, добавь фотоальбомы и персональные рекомендации. Подготовь нагрузочный стенд в Yandex Cloud с запуском через GitHub Actions. [Репозиторий Gatherly](https://github.com/dmgoldberg1/Gatherly)

## 1. Перенос бэкенда на Python

- Изучи текущие HTTP-контракты, схему и миграции PostgreSQL, интеграционные тесты, Docker Compose, Terraform, Ansible и GitHub Actions. Переиспользуй существующие SQL-запросы, сценарии запуска и инфраструктуру.
- Используй FastAPI, Uvicorn и Psycopg 3 с параметризованным SQL и ограниченным пулом соединений. Зафиксируй зависимости.
- Сохрани HTTP-маршруты, форматы ответов, коды ошибок, поведение фронтенда и совместимость с существующими данными, хешами паролей и токенами. Перенеси уведомления, outbox и правила записи на события и очереди ожидания. Проверь семантику при параллельных запросах.
- Прогони существующие HTTP smoke- и интеграционные тесты на Python-бэкенде до добавления новых функций. После проверки совместимости переключи штатную сборку, Compose и CI на Python.

## 2. Фотоальбомы

- Добавь создание, загрузку и просмотр фотоальбомов через веб-интерфейс. При создании альбома проверь права пользователя и выдай короткоживущий подписанный токен, привязанный к альбому.
- Для каждой фотографии реплика локально проверяет токен, декодирует изображение и готовит миниатюру и версию для галереи через Pillow. Для Compose используй общий том, для облака — Yandex Object Storage через boto3.
- Выполняй обработку вне event loop, сохраняя HTTP-запрос активным до её завершения. Ограничь размер входного файла, число пикселей и число параллельных обработок на реплику. Путь загрузки фото, включая проверку токена, должен обходиться без SQL.
- При публикации проверь готовность и принадлежность фото альбому и сохрани метаданные пакетно в короткой транзакции. Повтор публикации должен быть безопасным.

## 3. Персональные рекомендации

- Добавь API и блок «Рекомендовано вам». Используй `cointegrated/rubert-tiny2` через Sentence Transformers на CPU. Зафиксируй ревизию модели. Один фоновый процесс вычисляет векторы из названий и описаний новых и изменённых событий и публикует обновлённый снимок каталога. Реплики загружают готовый снимок.
- Строй профиль пользователя как взвешенное среднее векторов посещённых событий. Давай больший вес недавним посещениям. Для MVP используй прошедшие события со статусом `GOING` как приближение к посещению. Опиши это допущение в README.
- Ранжируй предстоящие публичные события по косинусному сходству через NumPy. Исключай события, на которые пользователь уже записался. При пустой истории показывай популярные предстоящие события.
- Храни компактный профиль в PostgreSQL, кэшируй его на реплике, а векторы кандидатов бери из локального снимка. Проверь, что при тёплом кэше весь запрос рекомендаций, включая авторизацию, обходится без SQL.

## 4. Стенд в Yandex Cloud

Топология включает один Envoy, от 1 до 10 реплик Gatherly, один PostgreSQL, Object Storage и отдельную VM для k6. Каждая реплика, Envoy, PostgreSQL и мониторинг (Prometheus/Grafana) размещаются на отдельных VM. Число реплик задаёт параметр `replicas` в конфиге; всего создаётся `replicas + 4` VM. Используй существующие Terraform и Ansible. Настрой обнаружение реплик и health checks. Для переключения `round_robin` и `least_request` используй файловый CDS с атомарной заменой конфига Envoy. Перед прогоном проверь, что новая политика активна и прокси видит нужное число здоровых реплик.

Учти суммарный бюджет соединений PostgreSQL, включая фоновые процессы. Проверки и сбор метрик каждой реплики должны обходиться без повторного опроса общей БД. Сохрани отдельную проверку доступности PostgreSQL.

## 5. GitHub Actions

Добавь отдельный workflow с ручным запуском через `workflow_dispatch` и версионируемым конфигом. Параметры запуска переопределяют значения по умолчанию. Валидируй итоговый конфиг до облачных изменений. Передавай один итоговый конфиг между джобами и прикладывай его к результатам.

| Параметр | Значение по умолчанию |
| --- | --- |
| `replicas` | `3`, допустимый диапазон `1–10` |
| `policy` | `round_robin` |
| `duration` | `180s` |
| `feed_rps` | `50` |
| `recommendations_rps` | `30` |
| `photo_upload_rps` | `5` |
| `photo_start_after` | `60s` |
| `seed` | `42` |

| Джоб | Задача |
| --- | --- |
| `cleanup_workspace` | Очистить временные файлы, принадлежащие нагрузочному стенду. Область очистки ограничена рабочими файлами этого стенда. |
| `deploy` | Собрать Python-образ, развернуть или обновить стенд через Terraform и Ansible и дождаться готовности прокси и реплик. |
| `update_config` | Применить изменения к уже поднятому стенду с текущим образом приложения. При смене политики обновить Envoy, при смене `replicas` изменить число реплик. Параметры RPS и длительности передать только в k6. Сохранить PostgreSQL, Object Storage и остальные ресурсы, которых изменение не касается. Повторное применение того же конфига должно быть безопасным. |
| `load_test` | Получить итоговые параметры, сверить фактическое число здоровых реплик с `replicas`, подготовить тестовые данные и запустить k6 на отдельной VM через Envoy. |

Поддержи режим `deploy_and_test` с последовательностью `cleanup_workspace → deploy → load_test` и режим `update_config` с последовательностью `cleanup_workspace → update_config` и опциональным `load_test`. Сериализуй операции с одним стендом, чтобы конфигурация не менялась посреди чужого прогона.

## 6. Нагрузка и проверка

- Запускай в k6 три параллельных сценария с заданным темпом поступления запросов: публичная лента, персональные рекомендации и загрузка фото. До измеряемой фазы подготовь аккаунты с разной историей, токены, альбомы и фото нескольких размеров. Для сравнения политик используй одни и те же тестовые данные и входной темп.
- Сохраняй итоговый конфиг и отчёт GitHub Actions. По каждому сценарию покажи заданный темп, фактический успешный RPS, p95, p99, ошибки и `dropped_iterations`. Собирай доступную диагностику при падении прогона.
- В Grafana покажи распределение запросов, CPU и очередь обработки по репликам, а также нагрузку PostgreSQL.
- Проверь совместимость переноса, загрузку и публикацию фото, рекомендации с историей и без неё, короткий прогон через прокси с одной и тремя репликами и обновление конфигурации запущенного стенда.
- В README опиши локальный запуск, параметры workflow, обновление конфига и чтение отчёта. В финале перечисли фактически выполненные проверки, облачные сценарии и максимальное проверенное число реплик.
